## Finding 1: Webhook endpoint buffers entire request body without size limit before token validation

**Verdict**: ✅ CONFIRMED — Severity: HIGH

**Evidence**: 
- `$token.ts` line 14: `const rawBody = await request.text()` — full body buffered into memory.
- Line 17: `const result = await receiveIncomingWebhook(urlToken, rawBody, signatureHeader)` — token validation happens HERE.
- Verified `receiver.ts` line 74: `handleIncomingWebhook(urlToken, rawBody, signatureHeader, ...)` → `incoming.ts` line 140: `deps.findByToken(urlToken)` — the DB lookup for token validation is deep in the call chain, long after the body is fully buffered.
- No `Content-Length` check, no streaming, no size limit anywhere in the chain.

**Impact**: Any unauthenticated attacker can POST arbitrarily large payloads to `/api/webhook/<any-string>` and the server will buffer the entire body in memory. No valid webhook token is required. This is a genuine memory exhaustion vector.

**Severity Rationale**: HIGH is appropriate. While a reverse proxy (nginx, Cloudflare) would typically enforce body size limits, the application should not rely solely on that. The endpoint is unauthenticated and publicly accessible.

## Finding 2: Global QueryCache onError fires toasts on background refetch failures

**Verdict**: ✅ CONFIRMED — Severity: MEDIUM

**Evidence**: 
- `router.tsx` lines 14–22: `new QueryCache({ onError: (error, query) => { toast.error(error.message, { action: { label: "retry", onClick: query.invalidate } }); } })`.
- No check for `query.state.data !== undefined` to distinguish initial loads from background refetches.
- React Query's `onError` on QueryCache fires for ALL query failures: initial loads, background refetches, and prefetches.

**Impact**: Transient network issues during background refreshes will produce spurious error toasts. The "retry" action is misleading for background refetches (the user didn't initiate the request). This creates noisy UX where the app appears broken even when cached data is still displayed.

The suggested fix (`if (query.state.data === undefined)`) is the standard React Query pattern for this.

## Finding 3: Webhook handler returns distinct status codes per error state — token enumeration

**Verdict**: ✅ CONFIRMED — Severity: MEDIUM

**Evidence**: 
- `incoming.ts` lines 142–167 return distinct status codes:
  - Line 142–148: `webhook === null` → `404 "Webhook not found"`
  - Line 151–157: `!webhook.enabled` → `410 "Webhook is disabled"`
  - Line 161–167: `!verification.valid` → `401 "Invalid signature"` or `"Missing X-DCRM-Signature header"`
- These distinct codes allow an attacker to determine:
  1. Whether a token is valid (404 vs non-404)
  2. Whether the webhook is disabled (410)
  3. Whether HMAC is configured (401 with "Missing X-DCRM-Signature")

**Severity Rationale**: MEDIUM is appropriate. Practical impact is limited:
- Single-user CRM — the attack surface is small.
- Webhook tokens are generated by `nanoid()` (high entropy, unpredictable).
- The tokens are exposed in URLs anyway (sent to third-party services).
- But the principle is valid — the 404 vs 410 distinction leaks information unnecessarily.

The suggested fix (collapse "not found" and "disabled" into the same 404 response) is reasonable defense-in-depth.
